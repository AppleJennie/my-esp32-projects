## 二、关键技术模块

### 2.1 端侧 AI 推理引擎

**技术选型**：TensorFlow Lite for Microcontrollers (TFLM)

**设计决策**：原始卧室音频涉及高度隐私，传统方案将音频上传云端分析存在三个问题——流量成本高（8 小时连续监测）、隐私风险大、网络依赖强。本系统选择在 ESP32-S3 端侧完成全部推理。

**处理流程**：

```
麦克风采集 (16kHz, 16bit, 单声道)
         │
         ▼
    ┌──────────────┐
    │  音频分帧     │  每 100ms 一帧 (1600 样本)
    │  Hamming 加窗 │  帧长 512 → 32ms, 帧移 320 → 20ms
    └──────┬───────┘
           ▼
    ┌──────────────┐
    │  FFT 频谱     │  ESP-DSP dsps_fft2r_fc32 (512点)
    │  Mel 滤波器组 │  26 通道三角滤波器 (80Hz~4000Hz)
    │  Log + DCT   │  → 13 维 MFCC
    └──────┬───────┘
           ▼
    ┌──────────────┐
    │  特征拼接     │  49 帧 × 13 维 = 637 维特征向量
    │  (约 3 秒)   │  滑动窗口 50% 重叠
    └──────┬───────┘
           ▼
    ┌──────────────┐
    │  TFLM 推理    │  量化 CNN 模型
    │  10 种算子    │  Conv2D → MaxPool → Mean → FC → Logistic
    │  PSRAM 张量   │  arena 512KB @ 外部 PSRAM
    └──────┬───────┘
           ▼
    ┌──────────────┐
    │  后处理判定   │  连续 2 帧 prob > 0.6 → 鼾声事件开始
    │  事件检测     │  连续 3 帧 prob < 0.6 → 鼾声事件结束
    └──────┬───────┘
           ▼
      输出: 鼾声概率 / 鼾声事件 / 鼾声时长
```

**内存优化策略**：ESP32-S3 内部 DRAM 仅 512KB，需同时服务 Wi-Fi 协议栈、LVGL 图形、音频编解码等多任务。TFLM 张量运算中间结果体积较大，通过 `heap_caps_malloc(..., MALLOC_CAP_SPIRAM)` 将张量 Arena 分配至外部 8MB PSRAM，避免内部 DRAM 溢出。模型算子按需注册（仅 10 种），减少 MicroMutableOpResolver 内存开销。

**容错设计**：当 TFLM 模型加载失败（如 PSRAM 不足、算子不兼容）时，系统自动降级为启发式 Mock 推理（基于音频能量 + 低频比例 + 能量方差的 sigmoid 评分），保证核心功能不中断。

### 2.2 多源传感器数据融合

**设计动机**：单一传感器在复杂睡眠场景下不可靠——雷达可测心率但无法判断鼾声；麦克风可测鼾声但无法判断用户是否在床；环境传感器提供背景但无法独立做出健康判断。多源融合是提升监测准确性的关键。

**融合架构**：

```
              ┌─────────────────────────────────────┐
              │         Fusion Task (每秒 tick)      │
              └──────────────┬──────────────────────┘
                             │
        ┌────────────────────┼────────────────────┐
        ▼                    ▼                    ▼
  ┌──────────┐        ┌──────────┐        ┌──────────┐
  │ 音频特征  │        │ 雷达特征  │        │ 环境特征  │
  │ MFCC+    │        │ 心率/呼吸 │        │ 温湿度/   │
  │ RMS+ZCR  │        │ 体动/存在 │        │ 光照      │
  └────┬─────┘        └────┬─────┘        └────┬─────┘
       │                   │                    │
       └───────────────────┼────────────────────┘
                           ▼
              ┌─────────────────────────┐
              │  多证据融合引擎          │
              │  120s 环形缓冲          │
              │  ┌───────────────────┐  │
              │  │ 10s/30s 滑动窗口   │  │
              │  │ 统计特征提取       │  │
              │  └───────┬───────────┘  │
              │          ▼              │
              │  ┌───────────────────┐  │
              │  │ 融合状态机         │  │
              │  │ Normal → Snore    │  │
              │  │ → Suspected_Apnea │  │
              │  │ → Movement_Artif. │  │
              │  └───────┬───────────┘  │
              │          ▼              │
              │  ┌───────────────────┐  │
              │  │ 证据评分 + 硬性抑制│  │
              │  │ · 体动>20抑制apnea│  │
              │  │ · 基线无效降置信度│  │
              │  │ · 音频缺失禁snore │  │
              │  └───────────────────┘  │
              └─────────────┬───────────┘
                            ▼
              ┌─────────────────────────┐
              │     SleepDataCenter      │
              │  统计仓库 + 评分引擎      │
              │  输出: 评分/风险/建议     │
              └─────────────────────────┘
```

**新鲜度管理**：各数据源更新频率不同——音频每秒 10 帧、雷达每秒 1 次、环境每 5 秒 1 次。系统为每种数据设定独立超时阈值（音频 1.5s、雷达 5s、环境 30s），超时数据自动清零，避免基于过期数据做错误判断。

**硬性抑制规则**：
- 体动级别 > 20 → 抑制呼吸暂停判定，优先标记为体动伪影
- 基线学习未完成 → 不允许输出高置信度呼吸暂停事件
- 音频数据缺失 → 禁止输出鼾声相关风险

### 2.3 睡眠质量评估算法

**设计思路**：参考匹兹堡睡眠质量指数（PSQI）和美国睡眠医学会（AASM）成人睡眠呼吸暂停判读规则，将关键临床指标量化为工程可实现的扣分规则。

**评分模型**：

```
睡眠评分 S = 100 - Σ(扣分项)

扣分项权重设计：

┌────────────────┬──────────┬────────────────────────────┐
│  维度          │  扣分值   │  触发条件                   │
├────────────────┼──────────┼────────────────────────────┤
│  血氧饱和度     │  -15     │  min SpO₂ < 90%            │
│                │   -5     │  avg SpO₂ < 95%            │
├────────────────┼──────────┼────────────────────────────┤
│  心率          │  -10     │  HR > 100 或 HR < 50 bpm   │
├────────────────┼──────────┼────────────────────────────┤
│  呼吸幅度      │  -10     │  幅度 < 0.3 (归一化值)      │
├────────────────┼──────────┼────────────────────────────┤
│  呼吸节律      │  -10     │  变异系数 CV > 0.3          │
├────────────────┼──────────┼────────────────────────────┤
│  体动          │  -10     │  夜间体动次数 > 20          │
│                │   -5     │  夜间体动次数 > 10          │
├────────────────┼──────────┼────────────────────────────┤
│  鼾声          │  -10     │  检测到鼾声事件             │
├────────────────┼──────────┼────────────────────────────┤
│  环境噪声      │   -5     │  平均环境音量 > -20 dBFS    │
└────────────────┴──────────┴────────────────────────────┘

风险分级: S ≥ 80 → 低风险 / 60 ≤ S < 80 → 中风险 / S < 60 → 高风险
```

**呼吸暂停专项评估**（独立于通用评分）：

针对阻塞性睡眠呼吸暂停（OSA）临床特征，额外计算专项指标：
- **rREI**（呼吸事件指数）：每小时呼吸暂停/低通气事件次数
- **T90**：SpO₂ < 90% 的时间占比
- **低氧负荷**：血氧下降幅度 × 持续时间积分
- **心率代偿反应**：呼吸事件后心率上升幅度
- **亚型倾向**：阻塞性 / 中枢性事件比例

### 2.4 MCP 设备能力标准化

**技术选型**：Model Context Protocol (MCP)，基于 JSON-RPC 2.0

**设计动机**：传统智能家居设备需要通过 App 或预定义指令控制。MCP 协议使大模型能够自动发现并调用设备能力——LLM 作为 MCP Client，设备作为 MCP Server，通过标准化的 `tools/list` 和 `tools/call` 接口实现能力互通。

**协议实现**：

```
MCP 生命周期:
  1. initialize  → 握手 + 能力协商 (protocolVersion + serverInfo)
  2. tools/list  → 分页返回工具列表 (单包 ≤ 8KB, 带 nextCursor)
  3. tools/call  → 远程调用工具 + JSON 结果返回
```

**设备暴露的 AI 可调用工具（11 个）**：

| 类别 | 工具 | 功能 |
|------|------|------|
| 会话控制 | `self.sleep.start` | 开始睡眠监测 |
| | `self.sleep.stop` | 停止监测并生成报告 |
| 实时查询 | `self.sleep.status` | 监测状态 + 基线进度 |
| | `self.sleep.get_vitals` | 心率/呼吸率/血氧 |
| | `self.sleep.get_snore_status` | 鼾声统计 |
| | `self.sleep.get_environment` | 温湿度/光照/舒适度 |
| 风险评估 | `self.sleep.get_apnea_risk` | 呼吸暂停风险 + 亚型 |
| | `self.sleep.get_night_summary` | 整晚摘要 |
| | `self.sleep.get_sensor_quality` | 传感器在线状态 |
| | `self.sleep.explain_current_risk` | 风险来源解释 |
| 报告生成 | `self.sleep.generate_report` | 完整结构化报告 |

**安全设计**：工具分为 AI 可见（AI 大模型自动调用）和 User Only（用户手动触发）两级。系统级操作（重启/OTA/固件升级）仅限 User Only，防止 AI 误操作。

### 2.5 语音交互全链路

**技术栈**：ESP-SR AFE（音频前端）+ 云端流式 ASR + LLM + TTS

**链路流程**：

```
用户语音
  │
  ▼
┌────────────────┐
│ AFE 音频前端    │  AEC 回声消除 + VAD 人声检测 + 降噪
│ 本地离线处理    │
└───────┬────────┘
        ▼
┌────────────────┐
│ 唤醒词检测      │  ESP-SR WakeNet (离线)
│ (本地)         │  唤醒 → 进入 Listening 状态
└───────┬────────┘
        ▼
┌────────────────┐
│ OPUS 编码       │  16kHz → 压缩音频流
│ (60ms 帧长)    │  码率 ~32kbps
└───────┬────────┘
        ▼
┌────────────────┐
│ WebSocket 上传  │  全双工音频通道
│ 到云端          │
└───────┬────────┘
        ▼
┌────────────────┐
│ 云端 ASR        │  流式语音识别 → 文本
│ → LLM          │  大模型理解意图 → MCP 调用 / 文本回复
│ → TTS          │  文本 → OPUS 音频流
└───────┬────────┘
        ▼
┌────────────────┐
│ OPUS 解码播放   │  设备端实时解码 + I2S 扬声器输出
│ AEC 回声对消    │  设备播放时仍可识别用户打断语音
└────────────────┘
```

**对话打断（AEC）**：在设备播放 TTS 语音期间，AFE 回声消除模块实时对消扬声器回声。用户可在 AI 说话时直接发出新指令，系统自动中断当前播放并切换到 Listening 状态，实现边说边听的自然交互体验。

### 2.6 数据持久化与离线运行

**SD 卡日志系统**：
- 按日期组织目录：`/sdcard/sleep/YYYY-MM-DD/session_HH-MM-SS/`
- 实时 CSV：每秒写一行传感器原始数据
- 鼾声日志：每次鼾声事件的起止时间、持续时长、最大概率
- 报告文件：会话结束时自动生成 JSON 结构化报告 + TXT 可读报告

**NVS 持久化**：设备设置（Wi-Fi 凭证/音量/亮度/语言偏好/校准参数）通过 ESP-IDF Non-Volatile Storage 断电保存。

### 3.2 双板通信架构

本项目采用"主板 + UI 板"双 MCU 架构，通过 UART 2（GPIO19/20, 115200bps）实现双向实时通信：

```
┌─────────────────────────┐       UART2       ┌─────────────────────────┐
│     主板 (ESP32-S3)      │ ←────────────── → │     UI板 (ESP32-S3)      │
│                         │   MAIN (31字段)    │                         │
│  · AI 语音交互           │ ─────────────────►│  · LVGL 触摸屏 GUI       │
│  · 云端大模型对接         │                    │  · 本地音频采集          │
│  · MCP Server           │   SNORE (14+字段)  │  · 鼾声检测上报          │
│  · 多传感器融合           │ ◄─────────────────│  · 本地鼾声分析          │
│  · SD 卡日志             │                    │  · BLE 手表数据          │
│  · 睡眠评分算法           │                    │                         │
└─────────────────────────┘                    └─────────────────────────┘
```

**MAIN 协议（主板 → UI板）**：31 字段 CSV，包含雷达状态、心率/呼吸率、融合事件 ID、呼吸专项评分、基线进度、温湿度等，每秒发送一帧。

**SNORE 协议（UI板 → 主板）**：14+ 字段 CSV，包含鼾声概率、分贝、RMS、峰值、过零率、质量评分、SPO2 等，UI 板本地推理后上报。

## 四、技术创新点总结

| # | 创新点 | 技术内容 | 工程价值 |
|---|--------|---------|---------|
| 1 | **端侧 AI 推理** | ESP32-S3 上部署 TFLM 量化 CNN，MFCC 特征提取 + 实时鼾声检测 | 原始音频不出设备，保护隐私；无需云端流量成本 |
| 2 | **多模态证据融合** | 音频 + 毫米波雷达 + 环境传感器时间对齐，120s 环形缓冲 + 硬性抑制 | 克服单一传感器不可靠问题，降低假阳性 |
| 3 | **MCP 标准化协议** | 设备作为 MCP Server，通过 JSON-RPC 2.0 自动暴露能力给大模型 | LLM 直接操控物理设备，无需 App/预设指令 |
| 4 | **全链路语音化** | 离线唤醒 + 流式 ASR + LLM 理解 + TTS 播报 + AEC 对话打断 | 全程无接触操作，适合夜间场景 |
| 5 | **工程化内存优化** | PSRAM 张量 Arena、堆分配避免 static 陷阱、滑动窗口 50% 重叠 | 在 512KB DRAM 受限环境下稳定运行完整 AI 推理管线 |
| 6 | **双板协同架构** | 主板(融合+云端) + UI板(GUI+本地音频) 通过 UART CSV 协议解耦 | 功能分离，各板独立优化，通信协议简洁可靠 |

## 六、技术局限与改进方向

| 局限 | 当前方案 | 改进方向 |
|------|---------|---------|
| 模型精度 | 阈值后处理 (连续帧判定) | SD 卡累积数据 → 与 PSG 标准对比标定 → 迭代优化 TFLM 模型 |
| 血氧缺失 | 等待从板数据源 | 集成 BLE 指夹式血氧仪或反射式血氧模组 |
| 单人场景 | 雷达监测单人 | 引入 MIMO 雷达 + 多人分离算法 |
| 基线依赖 | 需 120 秒初始化学习 | 引入预训练基线模型，缩短冷启动时间 |
| 离线 LLM | 依赖云端大模型 | 评估 ESP32-P4 上的端侧小语言模型可行性 |
