# 小智 AI 睡眠监测伴侣 — 答辩材料

> 基于正点原子 ESP32-S3 开发板的 AIoT 睡眠监测系统

---

## 一、项目一句话定位

**基于 ESP32 的 AI 语音交互终端，集成本地鼾声检测、多传感器睡眠监测、触摸屏可视化与大模型语音对话能力，支持 Web 远程数据查看。**

---

## 二、硬件平台

| 组件 | 型号/规格 | 说明 |
|------|----------|------|
| 主控 | 正点原子 ATK-DNESP32-S3 | ESP32-S3 双核，Wi-Fi + BLE |
| 屏幕 | 4.3 寸 RGBLCD 触摸屏 | 800×480，LVGL 图形界面 |
| 音频 | ES8388 音频编解码 | I2S 数字音频，支持麦克风+扬声器 |
| 扩展 | XL9555 I2C 扩展芯片 | 扩展 GPIO 控制外设 |
| 存储 | SD 卡 | 传感器数据本地持久化 |
| 传感器 | 毫米波雷达 + 温湿度 + 光照 | UART1 接入，JSON 协议 |

**主动取舍：摄像头引脚与 SPI 屏幕复用冲突，且夜间场景隐私优先，故禁用摄像头，聚焦音频+传感器能力。**

## 三、核心功能

### 3.1 AI 语音交互
- **离线语音唤醒**：基于 ESP-SR / AFE 音频前端，本地识别唤醒词
- **流式语音对话**：麦克风 → OPUS 编码 → WebSocket 实时上传 → 云端 ASR+LLM+TTS → 设备播放
- **对话打断（AEC）**：设备端回声消除，边说边听
- **语音指令控制睡眠监测**：说"晚安"启动，说"起床"停止，说"查报告"生成报告

### 3.2 本地 AI 睡眠监测（端侧推理）
- **TFLM 神经网络**：在 ESP32 上运行量化模型，MFCC 特征提取（49×13 维）
- **推理策略**：每 3 秒滑动窗口推理，50% 重叠，输出鼾声概率
- **事件判定**：连续 2 帧概率 > 0.6 为鼾声开始，连续 3 帧 < 0.6 为结束
- **内存优化**：张量空间分配在 PSRAM，避免内部 DRAM 溢出

### 3.3 多传感器数据融合
通过 UART1（GPIO16/17，115200bps）接收外接传感器：

| 数据源 | 数据内容 | 用途 |
|--------|---------|------|
| 本地麦克风 | 音频 RMS、VAD、鼾声概率 | 鼾声检测、环境噪声评估 |
| 雷达传感器 | 人体存在、体动、心率、呼吸率 | 生命体征监测 |
| 环境传感器 | 温度、湿度、光照 | 睡眠环境评估 |

### 3.4 睡眠质量评分算法（0~100 分）
- SpO2 < 90% 扣 15 分，< 95% 扣 5 分
- 心率异常（>100 或 <50）扣 10 分
- 呼吸幅度偏浅 / 节律不稳定各扣 10 分
- 体动过多扣 5~10 分
- 鼾声扣 10 分，环境嘈杂扣 5 分
- 输出风险等级（低/中/高）+ 个性化改善建议

### 3.5 触摸屏 GUI（7 页面）
基于 LVGL 手写实现，OV-Watch 医疗级暗色风格：

| 页面 | 内容 |
|------|------|
| 概览页 | 睡眠评分仪表盘 + 4 指标卡片 + 6 功能入口 |
| 实时监护 | SpO2/心率/呼声/呼吸大字显示 + 体位/环境 |
| 呼声波形 | 实时呼声强度折线图 + 模拟声音波形 |
| 睡眠报告 | 昨晚数据汇总（评分/打呼/暂停/翻身/血氧） |
| 呼吸事件 | 时间线形式事件记录 |
| AI 建议 | 基于数据的风险解释与改善建议 |
| 设置 | WiFi/蓝牙/云端/亮度/夜间模式 |

### 3.6 Web 远程数据查看（自搭服务器）
- 自己电脑搭建服务端，设备通过 WebSocket 上报数据
- 网页端可视化展示：实时数据、历史趋势、睡眠报告
- （如支持双向）Web 端可远程下发指令控制设备

### 3.7 MCP 设备控制协议
设备端作为 MCP Server，通过 JSON-RPC 2.0 暴露能力：

| 工具 | 功能 |
|------|------|
| `self.sleep.start/stop` | 启停睡眠监测 |
| `self.sleep.status` | 查询监测状态 |
| `self.sleep.get_vitals` | 心率/呼吸/血氧 |
| `self.sleep.get_snore_status` | 鼾声统计 |
| `self.sleep.get_environment` | 环境数据 |
| `self.sleep.get_apnea_risk` | 呼吸暂停风险 |
| `self.sleep.generate_report` | 生成完整报告 |
| `self.audio_speaker.set_volume` | 音量控制 |
| `self.screen.set_brightness` | 亮度控制 |
| `self.AEC.set_mode` | 对话打断模式 |

## 五、AIoT 三层闭环体现

### 第一层：感知智能（端侧 AI）
- 麦克风 → MFCC 特征 → TFLM 神经网络 → 鼾声概率
- 雷达/环境传感器 → UART 接收 → SleepDataCenter 融合
- **关键：原始音频不出设备，隐私保护**

### 第二层：连接智能（网络 IoT）
- WebSocket / MQTT + UDP 混合协议
- OPUS 音频流 + JSON 控制指令双通道
- MCP 协议标准化设备能力暴露

### 第三层：交互智能（AI Agent）
- 用户语音 → 云端 LLM 解析意图 → MCP 调用设备能力 → TTS 反馈
- 触摸屏 GUI 提供高信息密度可视化
- Web 端实现远程跨端访问

## 七、技术创新点（答辩重点）

1. **端侧 AI 推理**：ESP32 资源受限环境下部署 TFLM 神经网络，本地实时鼾声检测
2. **多模态感知融合**：音频 + 雷达 + 环境传感器在设备端时间对齐与融合评分
3. **MCP 标准化协议**：设备能力自动暴露给大模型，AI Agent 直接操控物理设备
4. **全链路语音化**：唤醒 → 对话 → 控制 → 反馈，无需 App/触屏
5. **四端协同架构**：设备 + 触摸屏 + 语音 + Web，覆盖全场景使用需求
6. **工程化细节**：PSRAM 双缓冲、FreeRTOS 事件驱动、SD 卡日志、NVS 持久化

## 九、评委可能追问及应对

| 追问 | 回答 |
|------|------|
| "为什么没有摄像头？" | 引脚冲突 + 场景不需要 + 隐私优先 |
| "AIoT 和普通智能家居有什么区别？" | 普通智能家居是规则控制（if 温度高 then 开空调），我们是 AI 决策（大模型理解用户意图，自动选择调用设备能力） |
| "端侧模型准确率够吗？" | TFLM 轻量模型 + 滑动窗口后处理，未来可用 SD 卡积累的数据迭代优化 |
| "为什么不用云端做鼾声检测？" | 夜间需 8 小时连续监测，云端流量成本高；卧室音频涉及隐私，端侧处理是刚需 |
| "和手环监测有什么区别？" | 手环靠加速度计，我们靠音频 + 雷达，能检测鼾声和呼吸暂停，维度更丰富 |
| "Web 端能控制设备吗？" | 【如支持双向】可以，Web 下发指令 → 服务器 → WebSocket → 设备 MCP 执行；【如仅显示】目前主要是数据可视化，远程监控大屏 |
| "两个工程是什么关系？" | 同一系统的两种形态。主工程负责 AI 语音+端侧推理+传感器融合；触摸屏工程是 GUI 前端扩展，共享 sleep_data 数据接口 |
| "为什么不合并成一个工程？" | 资源权衡，LVGL 占用较多 PSRAM，双工程可分别针对语音和显示优化，后续通过 Kconfig 统一 |

## 十、演示建议流程

1. **喊唤醒词** → 设备响应（LED 亮）
2. **说"我要睡觉了"** → 屏幕显示"监测已启动"，LED 状态变化
3. **模拟鼾声/展示触摸屏** → 切到"实时监护"页/"呼声波形"页，数据实时更新
4. **说"我起床了"** → 监测停止
5. **说"生成睡眠报告"** → MCP 工具被调用，大模型语音播报报告
6. **（如有条件）展示 Web 端** → 电脑浏览器打开，显示同步的数据/图表
